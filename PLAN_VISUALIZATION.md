# GitHub Contributions Visualization

## Goal

Build a reusable visualization for exploring one person's GitHub contributions
across repository owners and repositories.

This repository already contains the collection and archival layer. The next
work should build on that layer instead of creating a second contribution
model or another GitHub client. The complete system has three boundaries:

1. **Monthly source archives** — the existing `YYYY-MM.json` files generated by
   `ghcontribs.monthly`.
2. **Visualization data organizer** — a new offline command in `ghcontribs`
   that reorganizes those archives into a compact index and per-repository
   detail files.
3. **Framework-independent TypeScript visualization** — a browser library that
   loads the derived files and renders the interactive owner/repository
   ecosystem.

The initial site will embed the browser library in Astro. Static site assets
can be served through Cloudflare Pages and the derived contribution data can be
published to R2, but neither Astro nor Cloudflare should be a dependency of the
Python organizer or the visualization library.

---

## 1. Current foundation

The following capabilities are already implemented and are inputs to this
plan, not future visualization work.

### Contribution model

`ghcontribs.contrib` defines immutable, timezone-aware contribution objects:

- `Issue`
- `PullRequest`
- `Review`
- `Comment`

Every top-level object has a contribution timestamp, a GitHub URL, and a
contribution type. Issues and pull requests contain their owner, repository,
number, and title. Pull requests additionally contain merge state and any
issues they close. Reviews contain their associated pull request, and comments
contain their associated issue or pull request.

The nested objects are context for the top-level contribution. For example, a
pull request nested inside a review identifies what was reviewed; it is not a
second contribution by the user.

### JSON serialization

`ghcontribs.json_utils` serializes and reconstructs the rich contribution
objects without losing subtype or nested data. The source JSON contract is
described by
[`schemas/v1/contributions.schema.json`](schemas/v1/contributions.schema.json).

The source type names are:

| Python type | `contrib_type` |
| --- | --- |
| `Issue` | `issue` |
| `PullRequest` | `pullRequest` |
| `Review` | `pullRequestReview` |
| `Comment` | `issueComment` |

### Monthly archives

The existing command:

```bash
python -m ghcontribs.monthly USERNAME \
    --output-directory contributions
```

queries GitHub and writes one UTC-calendar-month file per eligible month:

```text
contributions/
├── 2024-01.json
├── 2024-02.json
├── 2024-03.json
└── ...
```

Each file is an array of rich contribution records. Months without
contributions are represented by empty arrays, and collection stops at the
current UTC month.

These monthly files remain the authoritative archive. Derived visualization
files are disposable build artifacts and must be reproducible from them.

## 2. Repository structure

Keep the Python organizer in the existing package and add the visualization as
an independently buildable browser package:

```text
ghcontribs/
├── ghcontribs/
│   ├── contrib.py
│   ├── json_utils.py
│   ├── monthly.py
│   ├── byrepo.py              # planned organizer and CLI
│   └── tests/
├── schemas/
│   └── v1/
│       ├── contributions.schema.json
│       ├── visualization-index.schema.json
│       └── repository-details.schema.json
├── viz/
│   ├── package.json
│   ├── src/
│   ├── test/
│   └── demo/
└── PLAN_VISUALIZATION.md
```

Do not create a separate Python `data-builder` project. The organizer consumes
objects and JSON conventions already owned by `ghcontribs`. The `viz/` package
remains separate because it has a different runtime, toolchain, and potential
release lifecycle.

The Python and TypeScript implementations share only the generated JSON
contract. That contract is expressed as JSON Schema and mirrored by exported
TypeScript types.

The canonical schemas remain in the top-level `schemas/v1/` directory. Python
packaging maps that directory declaratively to the internal resource package
`ghcontribs._schemas.v1`, so installed organizers can load the same contracts
with `importlib.resources` without maintaining a second checked-in copy.

## 3. Visualization data contract v1

The organizer produces a complete static dataset:

```text
dist-data/
├── index.json
└── repos/
    ├── omsf/
    │   ├── lambdacron.json
    │   └── static-site-tools.json
    ├── openforcefield/
    │   └── openff-toolkit.json
    └── dwhswenson/
        └── ghcontribs.json
```

Both schemas use numeric `schema_version: 1`. Generated files do not contain a
build timestamp: wall-clock metadata would make identical source archives
produce different output. The index instead reports the source month range,
which is derived from the filenames, including empty months.

### Counts

Every count object has all four fields, even when some values are zero:

```json
{
  "issues": 2,
  "pull_requests": 4,
  "reviews": 7,
  "comments": 12
}
```

Each top-level archive record increments exactly one field by one. Counts are
unweighted. Nested pull requests, issues, and closing-issue references are
never counted independently.

The visualization vocabulary deliberately uses readable plural count keys.
The organizer owns the fixed mapping from the existing source
`contrib_type` values to these keys.

### `index.json`

`index.json` contains everything needed for the initial ecosystem view,
hover/focus summaries, contribution-type filtering, and month-range filtering.
No repository-detail request is required for those interactions.

Conceptually:

```json
{
  "schema_version": 1,
  "user": "dwhswenson",
  "source": {
    "first_month": "2013-01",
    "last_month": "2026-08"
  },
  "owners": [
    {
      "owner": "omsf",
      "repositories": [
        {
          "key": "omsf/lambdacron",
          "name": "lambdacron",
          "contributions": {
            "total": {
              "issues": 3,
              "pull_requests": 8,
              "reviews": 12,
              "comments": 17
            },
            "by_month": {
              "2025-11": {
                "issues": 1,
                "pull_requests": 2,
                "reviews": 0,
                "comments": 3
              },
              "2026-08": {
                "issues": 0,
                "pull_requests": 1,
                "reviews": 4,
                "comments": 2
              }
            }
          }
        }
      ]
    }
  ]
}
```

Important contract rules:

- `user` is required because source records identify repositories but do not
  identify the person whose archive is being built.
- An owner is a GitHub repository owner. It may be an organization or a
  personal account, so the schema and application should use `owner` rather
  than assume every group is an organization.
- Repository `key` is exactly `owner/repo` and is the stable identifier within
  a generated dataset.
- `name` and `owner` preserve the casing found in the source archive.
- `by_month` contains only months in which that repository has at least one
  top-level contribution. Missing months are interpreted as four zero counts.
- Owners and repositories are sorted deterministically by case-folded name,
  with the preserved spelling as the tie-breaker.
- The repository detail URL is derived from the key as
  `repos/{owner}/{repo}.json`; no filename field is needed.
- GitHub repository IDs, stars, downloads, and other metadata are omitted
  because they are not present in the monthly source contract.

Owner-level totals do not need to be duplicated in v1. The browser model can
sum the already-loaded repository counts for owner hover and focus states.

### Repository detail files

For example, `repos/omsf/lambdacron.json` contains:

```json
{
  "schema_version": 1,
  "key": "omsf/lambdacron",
  "owner": "omsf",
  "name": "lambdacron",
  "contributions": [
    {
      "url": "https://github.com/omsf/lambdacron/pull/38",
      "created": "2026-08-15T19:26:25+00:00",
      "contrib_type": "pullRequest",
      "owner": "omsf",
      "repo": "lambdacron",
      "number": 38,
      "title": "Remove provider block from module",
      "merged": false,
      "closes": []
    }
  ]
}
```

The elements of `contributions` retain the existing serialized source union,
including nested context. The repository-detail schema should reference the
definitions in
[`schemas/v1/contributions.schema.json`](schemas/v1/contributions.schema.json)
instead of defining a second canonical contribution shape.

Contributions are sorted by their top-level `created` instant, then URL, then
source contribution type. The detail panel derives the displayed repository,
number, and title from the top-level issue/PR or from the nested target of a
review/comment.

### Contract ownership and versioning

Treat these generated files as a public API:

- Use
  [`schemas/v1/visualization-index.schema.json`](schemas/v1/visualization-index.schema.json)
  for `index.json` and
  [`schemas/v1/repository-details.schema.json`](schemas/v1/repository-details.schema.json)
  for repository details.
- Give the existing contribution schema a stable local reference identity if
  needed for cross-schema validation.
- Validate organizer output against the schemas.
- Export corresponding TypeScript interfaces for the index, owner and
  repository summaries, count objects, repository details, and the four source
  contribution variants.
- Reject unsupported `schema_version` values when loading data in the browser.

Impact data will not be represented by nullable or placeholder v1 fields. A
later explicit schema extension can introduce its provenance, metrics, scoring
policy, and compatibility behavior once a real data source is selected.

## 4. Build the offline Python organizer

The proposed command is:

```bash
python -m ghcontribs.byrepo USERNAME \
    --input-directory contributions \
    --output-directory dist-data
```

This command is strictly an offline transformation. It must not accept a GitHub
token or make GitHub API requests.

### Input discovery and validation

The organizer should:

1. Inspect JSON files immediately inside the input directory.
2. Require monthly filenames to match `YYYY-MM.json` with a real calendar
   month, and process them in chronological filename order.
3. Decode each file through the existing rich-contribution JSON loader and
   require the top-level value to be an array.
4. Validate the serialized input against the existing contribution schema.
5. Convert each contribution timestamp to UTC and verify that it belongs to
   the month named by its source file.
6. Extract repository identity through the contribution model: directly for
   issues/PRs and through the nested target for reviews/comments.

An empty monthly file is valid and contributes to the index's source range.
An empty input directory is an error because it cannot define a source range.

Contribution URLs are treated as archive-wide record identifiers. Identical
repeated records may be coalesced so they do not double-count; repeated URLs
with different serialized content are errors. The implementation must also
reject case-insensitive owner/repository identity collisions with inconsistent
preserved spelling rather than generating two paths for the same GitHub
repository.

### Aggregation

After validation, group top-level contributions as:

```text
owner
└── repository
    ├── total counts
    ├── counts by source month
    └── chronologically sorted contribution records
```

Monthly buckets, rather than yearly buckets, match the source archive and allow
the browser to implement rolling one-, two-, and five-year ranges without
calendar-year approximation. Exact timestamps remain in repository details;
the index does not need daily buckets.

### Emission

Generate the complete output tree in one deterministic rebuild. JSON object
and array ordering, indentation, and trailing newline behavior should be fixed
so unchanged inputs yield byte-for-byte unchanged files.

The organizer should build into a temporary sibling directory, validate the
complete result, and only then replace the destination. This prevents a failed
build from leaving a mixture of old and new repository files. Replacement
semantics and any force option must be explicit in CLI help; the command must
not silently merge into an existing output tree.

Incremental generation is unnecessary for v1. The current archive size makes
a full rebuild simpler, and a full replacement automatically removes detail
files for repositories no longer represented by the source.

## 5. Test the organizer and contract

Tests should operate at three levels.

### Unit tests

Verify:

- source `contrib_type` to count-key mapping;
- repository identity extraction for every contribution subtype;
- top-level-only counting for reviews, comments, PR closing issues, and other
  nested context;
- UTC month membership, including non-zero timezone offsets;
- complete four-field zero/default count objects;
- deterministic sorting and path derivation.

### Validation and aggregation tests

Use fixed monthly inputs containing:

- all four contribution types;
- nested issue and pull-request context;
- an empty month;
- personal and organization owners;
- one owner with several repositories;
- records spanning several months and years;
- names with preserved mixed casing;
- identical and conflicting duplicate URLs;
- a timestamp outside its filename's UTC month;
- a case-insensitive repository identity collision.

Verify totals, sparse monthly buckets, source range, duplicate policy, failure
messages, and input/output schema conformance.

### Golden-directory test

Run the complete organizer against a small representative archive and compare
the emitted `index.json` and `repos/` tree byte-for-byte with checked-in
expected output. Run the build twice to demonstrate determinism. The same
golden output should become the visualization demo fixture so Python and
TypeScript exercise the same contract.

## 6. Design the TypeScript package around a mount API

Use a plain DOM API rather than making React, Astro, or another UI framework
part of the public boundary:

```ts
import { mountContributionEcosystem } from "@.../github-contributions-viz";

const visualization = mountContributionEcosystem(element, {
  dataUrl: "/contributions/index.json",
});
```

The returned controller should expose a small imperative surface:

```ts
interface ContributionEcosystem {
  destroy(): void;
  setContributionTypes(types: ContributionType[]): void;
  setMonthRange(range: { from: string; through: string }): void;
  setSizeMode(mode: "contributions" | "equal"): void;
  focusOwner(owner: string | null): void;
  selectRepository(key: string | null): void;
}
```

Month bounds are inclusive `YYYY-MM` values. Presets such as “one year” are UI
conveniences calculated from the dataset's `last_month`; they are not separate
model concepts.

The package should export only the mount API, its option/controller types, the
public data-contract types, and contribution filter types. Do not expose the
layout engine or D3 internals as public API.

A custom element can be added later as a convenience wrapper around the mount
API, but it is not the underlying implementation.

## 7. Separate loading, model, layout, rendering, and interaction

Keep the browser implementation layered so the organic geometry can evolve
without changing the data contract or interaction state:

```text
DataSource
   ↓
VisualizationModel
   ↓
Layout
   ↓
Renderer
   ↓
InteractionController
```

A reasonable source organization is:

```text
viz/src/
├── data/          # public types, schema checks, index/detail loading
├── model/         # counts, filters, ranges, sizing, selection
├── layout/        # owner grouping, packing, collision, stable positions
├── render/        # ecosystem, labels, controls, detail panel
├── interaction/   # hover/focus, selection, keyboard, zoom
└── index.ts       # public exports
```

The data layer should fetch `index.json` once, validate its version and shape,
and lazily load repository details on selection. Cache successful repository
loads in memory. A failed load should show an actionable panel error and remain
retryable rather than poisoning the cache.

## 8. Visualization behavior and milestones

### Milestone 1: schemas, model, and static overview

- Mirror and test the JSON contract in TypeScript.
- Render owner regions and rounded repository rectangles from the golden demo
  dataset.
- Show owner names, repository names where space permits, and counts for
  issues, pull requests, reviews, and comments.
- Size repository area from the sum of the four selected contribution counts,
  with a minimum visible rectangle size.
- Provide equal sizing as the only alternative mode.

This milestone is the first opportunity to test whether comments dominating a
repository's activity makes contribution-based area useful with real data.
Changing that policy later should be a model-level decision, not hidden layout
weighting.

### Milestone 2: stable organic layout

Develop and test:

- owner clustering;
- weighted rounded-rectangle packing;
- collision avoidance and padding;
- deterministic initial positions;
- stable approximate owner and repository positions;
- responsive reflow.

The core invariant is that filtering and resizing cause the ecosystem to morph
from its current arrangement rather than completely reshuffle.

D3 can provide low-level hierarchy, force, transition, and zoom primitives,
but custom rounded-rectangle collision or packing will likely be required. D3
must remain an implementation detail.

### Milestone 3: hover, focus, and keyboard interaction

Repository hover or keyboard focus should:

- emphasize the repository and its owner;
- expose the full repository name;
- show counts for the active filters and month range.

Owner hover or focus should emphasize its repositories and show summed counts.
Clicking or activating an owner should smoothly focus that region, reveal
labels hidden at overview scale, and provide a clear return-to-overview action.
Semantic focus behavior should be application state, not merely free-form
viewport zoom.

### Milestone 4: repository details

Selecting a repository should:

1. open the detail panel immediately with index-level summary data;
2. fetch its derived repository-detail URL;
3. show loading, success, empty, and retryable error states;
4. render contributions in chronological order with type, title, date, and
   GitHub link;
5. reuse cached successful data when reopened.

The detail view must handle all four source variants. Reviews display their
associated pull request, while comments display their associated issue or pull
request.

### Milestone 5: filtering and sizing

Initial controls should include:

```text
Contribution types:
[✓ PR] [✓ Issue] [✓ Review] [✓ Comment]

Time:
[All] [5 years] [2 years] [1 year]

Size by:
[Contributions] [Equal]
```

All filtering and contribution sizing operate from `index.json`. A missing
monthly bucket means zero contributions. With contribution sizing, filters
recompute weights and animate the current layout. Equal sizing ignores counts
for geometry but still updates displayed summaries.

Impact sizing is deliberately absent from v1 rather than shown as an inactive
or partially populated control.

## 9. Accessibility, responsiveness, and failure handling

The graphical layout cannot be the only way to access the information.

- Represent owners, repositories, active filters, selected repository, and
  contribution counts in semantic DOM.
- Make every selectable object keyboard reachable and operable.
- Give hover behavior an equivalent focus state.
- Keep a visible focus indicator and announce selection/detail loading changes
  appropriately.
- Respect reduced-motion preferences while preserving comprehensible state
  changes.
- Provide a usable non-graphical owner/repository list or equivalent semantic
  representation for assistive technology.
- Handle small viewports, unusually dense owners, very long names, zero results
  after filtering, index load failure, invalid schema versions, and repository
  detail failure.

Visual and browser tests should cover large and small repositories, dense owner
groups, stable filter transitions, responsive sizes, keyboard-only navigation,
reduced motion, zero-result filters, and retrying a failed detail request.

## 10. Package and demo the browser library

Build the package as TypeScript/ES modules with generated type declarations.
Vite library mode is a reasonable initial build system, while Vitest and a DOM
test environment can cover the public controller and model behavior.

`viz/demo/` should be a small framework-free page that imports the package and
mounts the visualization against the organizer's golden fixture. It is the
primary development and visual-regression surface, not a second application.

TypeScript tests should cover:

- schema-version and shape validation;
- all four contribution filters;
- inclusive monthly range calculations and rolling presets;
- sparse monthly buckets;
- contribution and equal sizing;
- owner focus and repository selection state;
- detail URL derivation, lazy loading, successful caching, and failed-load
  retry;
- `destroy()` removing listeners, observers, and generated DOM.

## 11. Astro and Cloudflare integration

Integrate with Astro only after the standalone library and demo are working.
The Astro component should provide a mount element, import the library in a
client-side script, and pass the data URL. It should not duplicate filtering,
layout, or data-loading logic.

The production architecture remains static from the browser's point of view:

```text
Cloudflare Pages: Astro HTML/CSS and versioned visualization JS
                              ↓
                     R2: derived data
                    ↙                ↘
              index.json       repos/owner/repo.json
```

Only `index.json` is required at initial load. Repository details are fetched
on selection and can be cached independently. The library bundle should use a
long-lived versioned cache policy; the mutable index should use a short policy
or deployment-specific cache busting.

Publishing to R2 is a later deployment step that consumes a fully validated
organizer output directory. R2 credentials, upload behavior, and cache
invalidation do not belong in the organizer's core transformation logic.

## 12. Implementation order and checkpoints

1. Use the finalized
   [`visualization-index.schema.json`](schemas/v1/visualization-index.schema.json)
   and
   [`repository-details.schema.json`](schemas/v1/repository-details.schema.json)
   contracts and their reference to the existing
   [`contributions.schema.json`](schemas/v1/contributions.schema.json).
2. Create representative monthly fixtures and expected derived output.
3. Implement input discovery, rich-record loading, validation, and repository
   identity extraction in `ghcontribs.byrepo`.
4. Implement four-type monthly aggregation and deterministic full-tree
   emission.
5. Add unit, schema, error-case, and golden-directory tests.
6. Scaffold `viz/`, mirror the data contract as TypeScript types, and load the
   golden output in the standalone demo.
7. Implement the model and static owner/repository overview.
8. Develop the stable organic layout against realistic data.
9. Add hover/focus, owner focus, and keyboard interaction.
10. Add lazy repository details and all four contribution variants.
11. Add contribution-type and monthly-range filters plus contribution/equal
    sizing.
12. Complete responsive, accessibility, reduced-motion, error-state, and
    visual regression work.
13. Package the browser library and integrate it into Astro.
14. Add R2 publication and deployment cache behavior.

The first major checkpoint is steps 1–8: a deterministic offline organizer
must transform existing monthly archives into validated derived data, and a
framework-free demo must render a convincing static ecosystem from that data.
This validates the most uncertain part—the organic rounded-rectangle layout—
without coupling it to Astro or deployment infrastructure.

## Explicit v1 assumptions and deferred work

- One organizer run consumes one user's complete monthly archive directory.
- The username is supplied explicitly because it is not stored in individual
  source records.
- Monthly files are the durable source of truth; generated visualization files
  are replaceable artifacts.
- Contribution URLs are archive-wide record identifiers.
- Comments participate fully in counts, filtering, sizing, and details.
- Monthly buckets are sufficient for index filtering; exact timestamps remain
  in repository details.
- Full deterministic rebuilds are sufficient; incremental generation is
  deferred.
- No GitHub lookup, repository-ID enrichment, impact provider, impact score, or
  impact sizing is included in v1.
- npm publication of the browser library is optional until its public API and
  layout behavior stabilize.
